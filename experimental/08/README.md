# 実験08: CoTを用いた1ステップ推敲の検証

このディレクトリでは、実験07で成功した「他者評価アプローチ」をさらに最適化するため、評価モデル（`qwen3.6`）の内部推論（CoT: `<think>` タグ）を有効にし、分析と修正訳の出力を1回のプロンプトで完了させる「1ステップ方式」を検証します。

## スクリプトの構成

- **`review.py`**:
  実験07のスクリプトをベースに、`LLMClient(think=True)` としてCoTを有効化しています。「問題点の洗い出し」と「修正訳の生成」を2回に分けていた実験07（2ステップ方式/擬似CoT）とは異なり、今回は1回のプロンプトで「分析を行い、最後に修正訳を出力せよ」と指示します。
  この方式では、思考過程（分析）がコンテキスト履歴に通常のテキストとして積まれず、隠された `<think>` ブロック内のみに留まるため、その違いが品質や一貫性に与える影響を確認します。
- **`batch.sh`**:
  `review.py` を用いた1ステップ推敲から、生成された修正訳の評価、集計までを全自動で行うバッチスクリプトです。

## batch.sh の動作

1. **推敲の実行**
   - **入力**: 
     - 原文: `examples/onde-en.txt`
     - ベースライン訳: `examples/tr/onde/gemma4/tr/onde-{lang}.txt`
   - **対象言語**: オランダ語 (`nl`)、チェコ語 (`cs`)
   - **推敲モデル**: `ollama:qwen3.6`
   - **出力先** (計2ファイル): 
     - 推敲後: `tr/onde-{lang}-reviewed.txt`

2. **評価**
   - **評価モデル**: `ollama:qwen3.6`
   - 各言語の推敲後の訳文に対して `trtools eval` を3回ずつ実行します (2言語 × 3回 = 計6回の評価)。
   - **出力先**: `evals/onde-{lang}-reviewed-{1,2,3}.json`

3. **集計**
   - `trtools agg` を使用して全6ファイルの評価結果の中央値を集計し、結果を `SCORES.txt` に出力します。

## 実行結果と分析

バッチスクリプトを実行し（所要時間: 221m44.407s）、以下のスコアを得ました。
※ベースラインは実験07の結果（2ステップ方式・CoT無効）です。

| 言語 | 実験07（2ステップ・CoT無効）| 実験08（1ステップ・CoT有効）| 実験08（1ステップ・CoT無効）|
| :--- | :---: | :---: | :---: |
| オランダ語 (nl) | **97点** | 96点 | 75点 |
| チェコ語 (cs) | **94点** | 86点 | 59点 |

### 考察

* **オランダ語**: 実験07の97点に対し96点とほぼ同等の結果でした。
* **チェコ語**: 実験07の94点から86点へと大幅に低下しました。評価スコアも79点・84点・95点と16点幅のばらつきが生じており、評価の安定性も低下しています。

  ログを詳細に分析した結果、原文4行目（`Luc: And I'm Luc, an experimental physicist...`）の推敲後テキストが `Luc: `（空）になっていることが判明しました。CoTが有効な場合、モデルが `<think>` 内の思考に集中して翻訳テキストの出力を省略するケースがあることを示しており、これはプロンプト改善だけでは解決が困難な**構造的問題**です。

  また、分析結果をチャット履歴に通常テキストとして蓄積する実験07の2ステップ方式と異なり、思考過程が `<think>` ブロック内のみに留まることで、前後の行との文脈一貫性も損なわれやすいと考えられます。

### フォールバック検証（`tr-fb/`）

空出力行をベース訳で補完する `apply_fallback.py` を作成し、チェコ語の推敲結果に適用しました（オランダ語は空出力なし）。結果はスコアがさらに低下しました（86点 → 74点、評価3回: 72点・89点・69点）。

原因の調査で、ベースライン訳 `onde-cs.txt` の4行目に `meteen`（オランダ語「すぐに」の意）という**外国語干渉**が混入していることが判明しました（正しいチェコ語は `hned` / `okamžitě`）。なおこれは今回の実験でオランダ語も対象言語に含まれていることとは無関係で、gemma4:26b がベースライン翻訳時に混入させた偶発的な干渉です。同ファイルには他にもフランス語干渉（55行目: `Of koncentrovat...`）や文法・表記の問題（`dvouštěbinový`、`za svým ohniska`）が存在します。

実験07の推敲（94点）はこれらの問題を修正できていましたが、実験08では空出力により問題行が単純に欠落していただけでした。フォールバックはその欠落を補完しますが、ベースライン自体に品質問題がある場合は問題行を復元するだけであり、解決にはなりません。**フォールバック処理は `review.py` には組み込まない**と判断しました。

### CoT無効（1ステップ・`--no-think`）追加検証（`tr-nt/`）

所要時間23m1.158sで完了。スコアはオランダ語75点（72・75・84）、チェコ語59点（49・59・73）とCoT有効よりさらに悪化しました。CoTなしでは分析を行わず即時出力するため推敲として機能せず、オランダ語では `wahrscheinlichkeit`（独語）の混入や `psi-squared` が英語のまま残存、チェコ語では `psi` → `pí` の誤変換や `coherent` → `souhlasný`（「合意」の意）という物理用語の誤訳が多発しました。

**最終結論**

1ステップ方式はCoT有無にかかわらず実験07の2ステップ・CoT無効方式に及ばない結果となりました。推敲には分析結果をチャット履歴に「通常テキスト」として蓄積する2ステップ方式が不可欠であり、CoTは推敲プロセスに不要なオーバーヘッドをもたらします。**今後の推敲プロセスは実験07の方式（2ステップ・CoT無効）を採用し、他の中リソース言語へと展開します。**

**補足：「思考の誘導」と「思考の委任」**

CoTに思考を委ねるより、2ステップ方式で思考を誘導する方が性能が出るという結果は直感に反するかもしれない。しかし、CoTはモデルに思考の内容と方向性を一任するのに対し、2ステップ方式は「まず問題を分析せよ（ステップ1）、次にその分析を踏まえて修正訳を生成せよ（ステップ2）」とタスクを明示的に分割することで、モデルの思考を外側から誘導している。さらに分析がチャット履歴に通常テキストとして蓄積されることで、後続行の推敲がその文脈を参照できる。CoT（`<think>` ブロック）は各ステップの内部で暗黙的に用いられており、重要なのはCoTの有無ではなく**タスク分割によって思考の方向を制御できるかどうか**であるといえる。

## 目的

実験07（2ステップ方式 / `--no-think`）と比較して、以下の観点でどちらのアプローチがより優れているか（品質・速度のバランスが良いか）を判断します。

1. **品質と文脈一貫性**: 分析結果をチャット履歴のコンテキストに「会話のテキスト」として残さないことが、前後の行の推敲品質に悪影響を与えないか。
2. **処理速度と実用性**: API呼び出し回数が半分になることと、CoT自体の処理オーバーヘッドを差し引きして、トータルの処理時間がどう変化するか。

この検証で最適な推敲プロセスが確定した後、他の中リソース言語へと適用範囲を拡大する予定です。
